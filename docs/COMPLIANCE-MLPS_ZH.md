# 等保 2.0 三级 —— MXID 应用层控制点对照

> 面向测评人员与实施方。给出 MXID **作为被测应用系统**在《GB/T 22239-2019 信息安全
> 技术 网络安全等级保护基本要求》第三级下,各控制点的实现方式与取证位置。

## 先读这一节:本文覆盖什么,不覆盖什么

等保 2.0 的安全通用要求分为**技术要求**与**管理要求**两大部分:

| 部分 | 本文覆盖 |
|---|---|
| 技术要求 · 安全物理环境 | ❌ 机房、门禁、消防 —— 属于承载环境 |
| 技术要求 · 安全通信网络 | ❌ 网络架构、通信传输、可信验证 —— 属于承载环境 |
| 技术要求 · 安全区域边界 | ❌ 边界防护、入侵防范、恶意代码防范 —— 属于承载环境 |
| **技术要求 · 安全计算环境** | ✅ **本文主体**(应用和数据层面) |
| 技术要求 · 安全管理中心 | 🔶 部分(审计数据汇总、集中分析) |
| 管理要求(制度/机构/人员/建设/运维) | ❌ 属于运营方的制度与人员 |

**换句话说:一次三级测评里,MXID 能直接回答的是"安全计算环境"这一块。**
机房、网络设备、防火墙、终端杀毒、以及制度文档和人员岗位,不是软件能提供的证据。

另有一项**不在等保范围、但三级系统通常一并要求**的:**商用密码应用安全性评估(密评)**。
MXID 当前使用 bcrypt / AES-GCM / Ed25519 / SHA-256,**未使用 SM2/SM3/SM4 国密算法**,
见文末"已知差距"。

## 8.1.4 安全计算环境

### 8.1.4.1 身份鉴别

| 要求 | 实现 | 取证位置 |
|---|---|---|
| 登录用户应进行身份标识和鉴别,标识唯一 | 用户名租户内唯一(数据库唯一约束);口令 bcrypt 加盐存储 | 控制台 → 用户;`mxid_user` 表 |
| 口令有复杂度要求并定期更换 | 长度/大小写/数字/特殊字符策略 + 历史重用检查 + 过期天数,均可配 | 控制台 → 设置 → 安全策略 |
| 具有登录失败处理功能(结束会话、限制次数、超时退出) | 失败 5 次锁定 15 分钟(可配),失败 3 次起要求验证码;会话同时受**空闲超时**与**绝对超时**约束 | 设置 → 安全策略;登录页实测 |
| 远程管理时防止鉴别信息在网络传输中被窃听 | 全站 HTTPS;应用层与 nginx 双写 HSTS;release 模式强制 `cookie_secure`,否则拒绝启动 | `internal/middleware/security_headers.go`;`deploy/nginx/prod.conf` |
| **应采用两种或两种以上鉴别技术,其中一种至少应使用密码技术来实现** | 口令 + 第二因素(TOTP / 短信 / 邮件),可按策略强制全员启用;未绑定因素的会话被**强制注册闸门**挡住 | 设置 → MFA 策略;`internal/domain/authn/enroll_gate.go` |

> ⚠️ **需提前与测评机构对口径**:上表最后一项中"其中一种使用密码技术"的判定,
> 各测评机构尺度不一。MXID 提供的第二因素为 TOTP(HMAC-SHA1/256)、短信、邮件,
> **不含**数字证书 / USBKey / 国密算法认证。若测评方要求证书类因素,需另行方案。

### 8.1.4.2 访问控制

| 要求 | 实现 | 取证位置 |
|---|---|---|
| 应对登录的用户分配账户和权限 | RBAC:角色 → 权限 → 主体绑定;支持组织/用户组/角色三类主体 | 控制台 → 权限管理 |
| 应重命名或删除默认账户,修改默认口令 | **release 部署不接受默认口令**:种子 `admin` 账户的口令明文写在公开仓库的迁移文件里,启动时若仍是该口令,则从 `MXID_BOOTSTRAP_ADMIN_PASSWORD` 取新口令,**未配置则账户仍可登录但欠一次改密**(`PwdGateMiddleware` 只放行改密接口,其余路由一律拦截),启动日志持续告警;两种情况下首次登录均强制改密 | `internal/bootstrap/admin_credential.go`;启动日志 |
| 应及时删除或停用多余的、过期的账户 | 禁用/锁定账户**立即切断其已有会话**(含 SSO 共享会话),不等待超时;删除用户同样立即撤销 | `app/run.go` 事件订阅;`app/session_revocation_test.go` |
| 授权主体配置访问控制策略,规定主体对客体的访问规则 | 控制台网关**硬性默认拒绝**:未在 `consoleProtectedRoutes` 登记的路由运行时 403,启动时告警 | `app/authz_console.go` |
| 访问控制的粒度应达到主体为用户级、客体为文件/数据库表级 | 权限点到操作级(如 `user.reset_password`);数据层 `tenantscope` GORM 插件强制行级作用域,失败即拒 | `pkg/tenantscope/` |
| 最小权限原则 | 内置角色按职责拆分;`super_admin` 为独立列而非角色绑定,授予/回收产生专门审计事件 | `mxid_user.is_super_admin`;审计事件 `user.super_admin.grant` |

### 8.1.4.3 安全审计

| 要求 | 实现 | 取证位置 |
|---|---|---|
| 审计覆盖到每个用户,对重要用户行为和重要安全事件进行审计 | 所有写接口经 catch-all 中间件记录;领域事件另有专门审计;登录、授权变更、PII 查看、超管授予等均单独成事件 | 控制台 → 审计日志 |
| 审计记录应包括事件的日期和时间、用户、事件类型、是否成功及其他相关信息 | 每条记录含时间、主体(id/名称/类型)、事件类型、成功/失败、资源、IP、User-Agent、地理位置、会话 ID | `mxid_audit_log` 表结构 |
| **应对审计记录进行保护,定期备份,避免受到未预期的删除、修改或覆盖等** | ① 无任何删除/修改审计记录的接口;② **防篡改哈希链**:每条记录进入链式摘要,并由 Ed25519 签名的检查点(anchor)定期锚定,任何改写都会被范围校验发现;③ 进入证据链的捕获发生在**业务事务内部**,捕获失败即回滚该业务写入,不存在「操作成功但无痕迹」;④ `make backup` 提供备份与**经验证的**恢复流程 | `docs/AUDIT-CHAIN-DESIGN.md`;`scripts/backup.sh`;`mxid-server -config=configs verify-audit` |
| **审计记录保存时间符合法律法规规定(≥6 个月)** | 默认保留 **365 天**;且设置**下限**(`MXID_AUDIT_MIN_RETENTION_DAYS`,默认 180),控制台**无法**保存低于下限的值,清理任务读取策略时也会向上钳制 | 设置 → 审计策略;`internal/domain/setting/audit_retention_floor_test.go` |
| 应对审计进程进行保护,防止未经授权的中断 | 证据链捕获由 GORM 插件在业务事务内完成,**不是可单独停掉的旁路进程**;供查询展示的 `mxid_audit_log` 行为尽力写入,失败时以结构化日志行兜底记录全部字段,并计入 `mxid_audit_write_failed_total`(分区耗尽等结构性故障单独打标签)——**该计数器非零即应视为安全事件** | `internal/domain/audit/` |

### 8.1.4.4 入侵防范(应用层部分)

| 要求 | 实现 | 取证位置 |
|---|---|---|
| 应能发现可能存在的已知漏洞,并在充分测试评估后及时修补 | CI 每次提交跑 `govulncheck` + `golangci-lint`;依赖告警按锁文件实际版本区间逐条核实 | `.github/workflows/` |
| 应能够检测到对重要节点进行入侵的行为,并在发生严重入侵事件时提供报警 | 条件访问产生 `login.risk` 风险事件(异地/不可能旅行/新设备);暴力破解锁定、超管授予、OIDC 令牌重放均为独立安全事件;**命中的事件类型可推送到告警 Webhook**(经 outbox 保证不丢,五分钟冷却窗口合并风暴) | 设置 → 审计策略 → 告警 Webhook;`internal/domain/auditalert/` |
| 应遵循最小安装的原则 | 运行镜像为 alpine + 静态二进制,**以 uid 1000 非特权用户运行**,`/app` 只读;compose 编排额外 `read_only` 根文件系统、`cap_drop: ALL`、`no-new-privileges`;Helm 同等 securityContext | `deploy/dockerfile/Dockerfile`;`deploy/compose/docker-compose.yml` |

### 8.1.4.7 / 8.1.4.8 数据完整性与保密性

| 要求 | 实现 | 取证位置 |
|---|---|---|
| 采用密码技术保证重要数据在传输过程中的完整性/保密性 | 全站 TLS;OIDC ID Token 签名、SAML 断言 XML-DSIG 签名 | 协议端点实测 |
| 采用密码技术保证重要数据在存储过程中的完整性 | 审计链 HMAC + Ed25519 签名锚点(见 8.1.4.3) | `docs/AUDIT-CHAIN-DESIGN.md` |
| 采用密码技术保证重要数据在存储过程中的保密性 | 口令 bcrypt;OIDC 签名私钥、外部 IdP 客户端密钥、表单填充凭据等一律 **AES-256-GCM** 加密落库,主密钥(KEK)仅存于环境变量,永不入库;release 模式拒绝开发占位密钥,并维护已泄露开发 KEK 黑名单 | `pkg/crypto/`;`internal/bootstrap/config.go` 的 `validateSecrets` |

> ⚠️ 上述均为国际通用算法。**未使用国密 SM2/SM3/SM4**,见文末"已知差距"。

### 8.1.4.9 数据备份恢复

| 要求 | 实现 | 取证位置 |
|---|---|---|
| 应提供重要数据的本地数据备份与恢复功能 | `make backup` 生成自定义格式转储;`make backup-verify` **实际还原到临时库并校验** schema 版本与核心表后销毁 —— 未经还原验证的备份不计为备份 | `scripts/backup.sh` |
| 应提供异地实时备份功能 | 🔶 **属于部署拓扑**:MXID 不限制,可用 PostgreSQL 流复制 / WAL 归档到异地实现 | `docs/DEPLOYMENT.md` |
| 应提供重要数据处理系统的热冗余 | 🔶 **属于部署拓扑**:应用无状态可多副本(后台单写任务由 Postgres 咨询锁选主),数据库热备由承载环境提供 | `pkg/dlock/`;Helm chart |

> 备份注意事项(务必写入运维手册):转储文件**不含加密主密钥**,没有同一把 KEK
> 时恢复出来的密文无法解密,KEK 必须**异地单独备份**;Redis 中的会话不做持久化,
> 恢复后全员重新登录(符合预期);逻辑恢复到**新集群**会改变 PostgreSQL 的
> `system_identifier`,企业版许可需要重新激活。

### 8.1.4.10 剩余信息保护

| 要求 | 实现 | 取证位置 |
|---|---|---|
| 鉴别信息所在的存储空间被释放或重新分配前得到完全清除 | 口令仅以 bcrypt 摘要存储,不留明文;日志管道对任何键名形似凭据的字段做脱敏(输出 `***`) | `internal/bootstrap/logger.go`;`pkg/secure/` |
| 敏感数据所在的存储空间被释放或重新分配前得到完全清除 | 改密(管理员重置)、禁用、锁定、删除用户,均**立即撤销该用户全部命名空间的会话**(控制台/门户/SSO 协议会话);删除用户同时清理组织、用户组、角色绑定等派生行 | `app/run.go`;`app/session_revocation_test.go` |
| 强制改密真正生效 | 管理员重置口令后,该用户的会话**除改密接口外一律 403**,直至其自行设定新口令 | `internal/domain/authn/password_gate.go` |

### 8.1.4.11 个人信息保护

| 要求 | 实现 | 取证位置 |
|---|---|---|
| 应仅采集和保存业务必需的用户个人信息 | 用户表字段限于身份与联系必需项(用户名/邮箱/手机/显示名/头像),无冗余采集 | `internal/domain/user/model.go` |
| 应禁止未授权访问和非法使用用户个人信息 | 访问受 RBAC 约束;**管理员查看 PII 产生专门审计事件** `user.pii_view`;列表与日志中手机/邮箱/身份证/姓名经脱敏输出 | 审计日志按事件类型 `user.pii_view` 筛选;`pkg/mask/` |

## 8.1.5 安全管理中心(部分)

| 要求 | 实现 | 取证位置 |
|---|---|---|
| 应对分散在各个设备上的审计数据进行收集汇总和集中分析 | **审计记录写入即镜像到外部 syslog 采集器**(RFC 5424,支持 UDP / TCP / TCP+TLS),facility 13(log audit)。防篡改链证明"无人改写历史",而离机副本应对的是"有数据库权限的人整表删除" | `MXID_AUDIT_FORWARD_ADDR`;`pkg/auditsink/` |
| 审计记录保存时间符合法律法规规定 | 见 8.1.4.3 的留存下限 | — |
| 应能对网络中发生的各类安全事件进行识别、报警和分析 | 安全事件推送至告警 Webhook(见 8.1.4.4);Prometheus 指标覆盖审计写入失败、外发丢弃、分区健康等静默故障 | `/metrics` 端点 |
| 应对安全策略、恶意代码、补丁升级等进行集中管理 | 🔶 安全策略在 MXID 内集中且热生效(设置中心);恶意代码与补丁属于承载环境 | 控制台 → 设置 |

> **外发的设计约束(测评时常被追问)**:审计外发**绝不阻塞**审计写入。外发运行在
> 与所有写接口同步的路径上,若采集器卡住能阻塞它,一台故障的日志服务器就会拖垮整个
> 业务系统。因此采用有界队列,溢出即丢弃并计入 `mxid_audit_forward_total{result="dropped"}`
> —— **记录本身始终已落库**,丢失的只是镜像的完整性,该指标即为其可观测证据。

## 已知差距

| 项 | 说明 |
|---|---|
| **国密算法** | 当前为 bcrypt / AES-256-GCM / Ed25519 / SHA-256,**无 SM2/SM3/SM4**。这是三级测评"使用密码技术"判定与**密评**的核心分歧点。改造面涉及口令哈希、KEK/DEK、审计链摘要与许可签名,其中许可签名一旦更换,已签发的授权全部失效,需专门方案。 |
| **第二因素类型** | 仅 TOTP / 短信 / 邮件,无数字证书 / USBKey。若测评方对"其中一种使用密码技术"取严格解释,需另行方案。 |
| **告警通道** | 目前仅 Webhook。邮件与短信通道尚未接入(邮件与短信能力本身在产品内已具备,仅未接到告警链路)。 |
| **可信验证** | 三级要求基于可信根对启动与运行时进行可信验证。纯软件产品无法提供,需由可信计算平台 / TPM 支撑。 |
